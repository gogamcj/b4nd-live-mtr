# 09. 단계별 개발 계획

각 Phase는 **빌드 → 자동 테스트 → 수동 검증 → 오류 수정** 후 완료로 표시한다. 실패한 기능은 완료로 표시하지 않는다.
검증 환경 표기: 🐧 = 개발 클라우드(Linux)에서 검증 가능, 🪟 = Windows 실기(오디오 인터페이스·MIDI 장비) 필요.

## 의존 관계

```
1 → 2 → 3 → 4 → 6 → 7 → 12 → 13 → 14
          └→ 5 ─┘
1 → 8 → 9 → 10 → 11   (AI 트랙은 재생 엔진과 병렬 진행 가능, 결과물은 3의 프로젝트 포맷에 기록)
```

## Phase 1 세부 범위 (이번 구현)

1. CMake 프로젝트: JUCE 8 FetchContent, MSVC/Ninja 프리셋, `B4ND_ENABLE_ASIO` + `B4ND_ASIO_SDK_DIR` 옵션 (Phase 2 대비)
2. `b4nd_core` 정적 라이브러리: `TempoMap`, `OutputRouting`(클릭 보호 규칙), `TimeFormat`
3. 앱: 다크 `LookAndFeel`, 메인 창(최소 1280×720), 레이아웃
   - 상단 TransportBar: 프로젝트명, BPM, Key, 박자, 위치, PLAY/STOP/PAUSE/RESTART/EMERGENCY
   - 좌측 SidePanel: 프로젝트(곡 목록), AI 분석 메뉴(Phase 8 전까지 비활성 표시)
   - 중앙 TimelineView: 눈금자(마디), 트랙 헤더, 샘플 트랙 레인, 재생 헤드
   - 하단 MixerPanel: 채널 스트립 모형, 8개 출력 미터, StatusBar(장치/MIDI/VSTi/CPU/언더런)
   - LiveModeView: 전체 화면 전환(F11), 현재/다음 곡, 큰 버튼
4. 단축키: Space(재생/정지), Esc(비상 정지), Home(처음으로), F11(공연 모드)
5. 로그: `%APPDATA%/B4ND LIVE MTR/logs/` 파일 로그
6. Phase 1의 재생은 **가상 트랜스포트**(UI 타이머 기반 위치 진행)로, 오디오는 출력하지 않음. 실제 오디오는 Phase 2부터.
7. CI: GitHub Actions에서 Windows(MSVC) + Linux 빌드 및 core 테스트

## 일정 감각 (참고)

Phase 1~3이 "오디오가 나오는 MTR"의 최소 단위이며, 이 시점에서 연습실 실기 테스트를 한 번 해보는 것을 권장한다. MIDI/VST(4~7) 이후 Live Mode(12)를 앞당겨 리허설에서 사용하며 안정성을 축적하는 것이 공연 안정성 측면에서 유리하다.

## Phase 2 구현 결과 (2026-11-16)

- `b4nd_engine`(JUCE 비의존): 오디오 콜백 처리, SPSC 명령/이벤트 큐, 샘플 클럭 기반 트랜스포트, 5ms 페이드 정지·비상 정지, 출력 테스트 신호(Tone, Identify, Click/Guide Check, Walk), 출력별 피크, 언더런/과부하 감지
- `AudioDeviceController`: ASIO → WASAPI(Exclusive) → WASAPI(Shared) → DirectSound 순서, 저장 장치 복원, 저장 장치가 없으면 다른 장치로 대체하지 않음, 장치 분리 감지 후 같은 장치만 재연결(Live Mode에서는 수동)
- 오디오 설정 창(상태바 클릭 또는 Ctrl+,): 드라이버/장치/샘플레이트/버퍼(사양 값 ∩ 장치 지원 값), 지연, 드롭아웃, ASIO 드라이버 패널, 출력 테스트
- 검증: 엔진 단위 테스트(콜백 내 힙 할당 0 포함), Linux JACK 가상 8채널 장치로 열기/분리/재연결 자동 테스트(CI), Windows CI에서 ASIO SDK를 받아 ASIO 포함 빌드
- 남은 실기 검증(🪟): UR22C ASIO 실제 재생, USB 분리 시 동작, 드라이버 패널 버퍼 변경
- 제약: UR22C는 출력 2채널이라 8채널 출력 테스트는 장비 교체 후. 2채널용 분리 프리셋(OUT1 = MR 모노 PA, OUT2 = 클릭+가이드)은 Phase 3에서 추가

## Phase 3 구현 결과 (2026-11-16)

- 엔진: 곡 단위 `PlaybackPlan`(트랙, 클립, 템포맵, 클릭음)을 메시지 스레드에서 만들어 원자적으로 넘기고, 정지 상태에서만 교체. 이전 플랜은 메시지 스레드에서 해제
- 버스 믹스: Main / Click / Guide / Extra / Monitor / Aux. 트랙 볼륨·팬·뮤트·솔로(블록 내 램프), 클릭·가이드는 솔로 영향 없음, 마스터 페이더는 Main(PA)만
- 인이어 모니터 버스 = 클릭 + 가이드 (+ 선택적으로 MR 일부). PA 출력에는 클릭/가이드/모니터가 엔진 단계에서도 차단
- 클릭: 템포맵·박자표(6/8 포함) 추종, 첫 박 악센트, 샘플 단위 정확도
- 2출력 장치(UR22C) 자동 프리셋: OUT1 = MR 모노 합(PA), OUT2 = 클릭+가이드(인이어). 4출력 이상은 표준 8채널 맵
- 미디어: WAV / AIFF / FLAC / Ogg / MP3를 백그라운드에서 장치 샘플레이트로 변환해 RAM에 적재, 누락 파일·손상 파일 표시, 메모리 사용량 표시
- UI: 타임라인에 오디오 파일 드래그 앤 드롭(트랙 위 = 교체, 빈 곳 = 새 트랙), 파형, NO MEDIA / LOADING / MISSING 표시, 실제 라우팅 기준 출력 표시, 출력 수에 맞춘 미터
- 검증
  - 엔진 오프라인 렌더 테스트 14개(출력 위치, 클릭 타이밍, 템포 변경, 6/8 악센트, 솔로 안전, 2출력 분리, 플랜 교체, 블록 분할, 곡 끝, 오디오 스레드 힙 할당 0)
  - 미디어 테스트 7개(44.1k → 48k, 96k → 48k 변환 후 음정·길이·시작 위치, AIFF/FLAC, 누락/손상 파일, 6채널 파일, 캐시)
  - Linux JACK 가상 장치 실재생(CI): 8출력에서 MR이 OUT1/2, 클릭이 OUT3과 인이어 7/8에만. 2출력에서 OUT1 MR 모노, OUT2 클릭. DSP 최대 부하 약 4~7%
- 남은 실기 검증(🪟): UR22C로 실제 MR + 클릭 분리 청취, 긴 곡 RAM 사용량
- 다음으로 미룬 항목: SQLite 프로젝트 저장/열기(Phase 3b로 분리), WAV 캐시/메모리 매핑 재생, 출력 라우팅 편집 UI

## Phase 3b 구현 결과 (2026-11-16)

- 프로젝트 저장/열기: `.b4nd` 패키지 폴더 + SQLite `project.db` (docs/08 스키마 v1)
- 새로 만들기 / 열기 / 저장 / 다른 이름으로 저장 (좌측 상단 버튼, Ctrl+N / Ctrl+O / Ctrl+S / Ctrl+Shift+S). Live Mode와 재생 중에는 열기/새로 만들기 잠금
- 변경 5초 후 자동 저장, 프로젝트 IO 스레드에서만 DB 접근 (오디오 스레드와 무관)
- 백업: 열 때 + 30분마다, 최근 20개
- 비정상 종료 감지: `session.lock`이 남아 있으면 다음 열기 때 알리고 이전 백업 복원을 선택할 수 있음 (Esc는 아무것도 하지 않음)
- 시작 시 마지막 프로젝트 자동 열기, 열 때 누락 미디어 경고
- 상태바 PROJECT 항목: 저장 시각 / 저장 중 / 저장 실패
- 검증: DB 테스트 9개 (저장-열기 왕복, 재저장 시 잔여 데이터 없음, 실패 시 롤백, PA 클릭 금지 제약, 손상·타 DB·신버전 거부, 페이지 손상 감지, 백업 20개 유지와 복원, 상대 경로, 한글 이름). CI에서 실제 앱으로 저장 → 다시 열기 → 강제 종료(kill -9) 후 감지까지 확인

## Phase 4 구현 결과 (2026-11-16)

- 외부 MIDI 음원 모듈: 모듈 프로필(포트, 채널, Bank MSB/LSB, Program, 볼륨/팬 CC, 지연 보정, 전송 순서, 간격, 안정화 시간), 상태 표시(NO PORT / DISCONNECTED / CANNOT OPEN / PREPARING / READY), TEST NOTE, SEND PRESET
- MIDI Out 전용 스레드: 엔진이 보낸 이벤트를 정해진 시각에 전송. 오디오 출력 지연과 모듈 지연을 보정
- 포트 관리: 1초마다 확인, 분리 감지, 같은 포트가 돌아오면 다시 열고 프리셋 재전송
- Note 복구: 정지·이동·비상 정지·곡 끝·곡 교체 때 Note Off + CC64 0 + CC123. 오디오 장치가 끊기면 MIDI 스레드가 직접 해제
- `.mid` 파일 드래그 앤 드롭 → EXT MIDI 트랙(음표 블록 표시), 모듈·채널 지정, 프로젝트에 저장(스키마 v2, v1 자동 업그레이드)
- Live Mode 상태줄과 좌측 패널, 상태바에 모듈 상태 표시
- 검증
  - 코어 MIDI 테스트 4개: PPQ·템포 변환, 같은 시각 순서, Note 추적과 해제, Preset Recall 순서와 간격
  - 엔진 MIDI 테스트 7개: 콜백별 전송 시각, 지연 하한, 네 가지 정지에서 해제, Locate 후 중복 Note Off 없음, 뮤트/솔로, 곡 교체, 오디오 스레드 할당 0
  - MIDI 출력 테스트 6개 (가짜 포트 사용)
    - SMF 읽기
    - 전송 시각: 일찍 나가지 않고 중앙값 0.1 ms 이내
    - Preset 순서와 READY 전환
    - 분리 → 재연결(식별자가 바뀌어도 이름으로 찾음) → 프리셋 재전송, 점유된 포트 표시
    - panic
    - 실시간으로 돌린 엔진 → 포트: 목표 시각 대비 최대 약 1 ms
  - DB 테스트 10개: 모듈과 MIDI 트랙 왕복, v1 → v2 업그레이드 포함
  - 실제 앱 (Linux, JACK 가상 장치): 재생 중 엔진 → MIDI 스레드 경로, 정지 후 남은 음 0, 모듈과 .mid가 있는 프로젝트 저장 → 다시 열기, .mid 누락 경고
  - CI
    - Linux 러너에 `snd-virmidi`가 있으면 ALSA 가상 MIDI 포트로 실제 전송 바이트를 받아 Program Change, Note On/Off 짝, CC123을 확인한다. 없으면 경고만 남긴다
    - Windows: Microsoft GS Wavetable Synth 포트를 이름으로 찾아 상태를 보고하는지 확인한다. CI 러너에는 오디오 출력이 없어 이 포트가 열리지 않으므로 CANNOT OPEN이 정상이고, 실제 전송은 Windows에서 확인하지 못했다
- 남은 실기 검증(🪟): 실제 모듈(USB-MIDI 인터페이스)로 소리, 프리셋 전환, USB 분리 후 재연결, 공연 중 Note 걸림 여부. 클라우드에는 MIDI 장치가 없어 확인하지 못했다

- 좌측 Audio to MIDI 버튼 활성화. 이제 AI 메뉴 6개가 모두 동작
- 검증
  - Python 테스트 34개 (변환 6개 추가, 정답을 아는 합성 스템)
    - 베이스 라인: 재현율 0.87, 정밀도 0.74, 시작 시각 중앙값 오차 2 ms, 겹치는 음 없음

## Phase 11 구현 결과 (2026-11-18)

자세한 동작은 04 문서 §11.

- MIDI 에디터(피아노롤): 타임라인에서 MIDI 트랙을 더블클릭하거나 Ctrl+E
  - 곡의 템포맵 위에 마디·박·그리드 선, 왼쪽 건반, 아래 벨로시티 줄
  - 노트 뒤에 오디오 트랙 파형을 깔아 듣는 소리와 맞춘다. AI로 변환한 파트는 원래 스템이 기본, 아니면 MR
  - 선택(클릭, Shift, 드래그 범위, 건반 클릭 = 그 음 전체), 이동, 길이 조절, 더블클릭 추가/삭제, 벨로시티 드래그
  - 퀀타이즈(1/4 ~ 1/32, 셋잇단), 이조(±1, ±12), 벨로시티 ±10, 삭제, 실행 취소/다시 실행(200단계), 되돌리기
- 저장은 SAVE를 눌러야 한다. 새 .mid 파일(`midi/<곡>/edit-<시각>/<원래 이름>.mid`)을 쓰고 트랙이 그 파일을 쓰게 바꾼다. 이전 파일은 지우지 않는다
  - 임시 파일에 쓴 뒤 옮긴다. 다시 읽어 노트 수가 맞을 때만 트랙을 바꾼다
  - 노트가 하나도 없으면 저장하지 않는다 (트랙을 끄거나 지우라고 안내)
- 공연 안정성
  - 재생 중에는 저장할 수 없다 (편집 초안은 만들 수 있음). 일시정지·정지 상태에서만 재생 계획을 바꾼다
  - Live Mode에서는 에디터가 닫히고 편집도 저장도 안 된다. 초안은 남아 공연 뒤에 이어서 할 수 있다
  - 같은 음이 겹치면 뒤 음이 시작하는 곳에서 앞 음을 끊고, 같은 시각 같은 음은 하나로 합친다. 노트가 걸려 남는 파일을 만들지 않는다
  - CC, 프로그램, 피치 벤드 같은 노트가 아닌 이벤트는 그대로 둔다
- 검증
  - 편집 모델 테스트 6개 (core): 이벤트 ↔ 노트 왕복, 선택 묶음 이동의 범위 제한, 퀀타이즈(강도, 끝 맞춤), 겹침 정리, 범위 선택, 실행 취소·다시 실행
  - SMF 저장 테스트 (midi): 편집 결과를 쓰고 다시 읽으면 같은 노트·컨트롤, 남은 임시 파일 처리, 쓸 수 없을 때 오류
  - 실제 앱 (Linux): AI 베이스 파트를 퀀타이즈 → 이조 → 삭제/실행 취소 → 노트 추가 → 저장 → 다시 열기에서 노트 수 +1, 추가한 음이 맨 앞, AI 파트 표시 유지, 모든 노트 시작이 1/16 그리드 위
  - 잠금: 재생 중 저장 거부, Live Mode에서 편집·저장 거부, 끄면 저장됨 (CI에 같은 검사)
  - Windows CI: 같은 편집과 저장
- 남은 검증: 마우스 편집 손맛(드래그, 스크롤, 확대)은 실제 Windows PC에서 확인 (🪟). 자동 검사는 버튼과 같은 함수를 부르지만 마우스 동작 자체는 사람이 봐야 한다
- 아직 없는 것: 건반 클릭으로 소리 듣기(오디션), 노트별 AI 신뢰도 표시, 여러 트랙 동시 편집, CC/피치 벤드 편집, 오래된 편집 파일 정리

## Phase 13 구현 결과 (2026-11-18)

- 세트리스트 창 (좌측 EDIT SETLIST, Ctrl+L)
  - 곡 추가(선택한 곡 다음에, 클릭 트랙 포함), 삭제(확인 창, 오디오 파일은 디스크에 남김), 위/아래로 이동, 제목·아티스트
  - 곡마다 쇼 안에서 시작하는 시각, 길이, BPM, Key, 오디오 상태(READY / LOADING / not in RAM / MISSING), 총 시간
  - 순서는 프로젝트 DB의 setlist_entry에 저장 (스키마 v5 그대로)
  - Live Mode와 재생 중에는 잠금 (이름 바꾸기는 재생 중 가능)
- 다음 곡 사전 로딩 (RAM 예산)
  - 세트리스트 전체 오디오(파일 헤더로 미리 계산)가 예산 안이면 전부 RAM에 둔다. 공연 중 디스크에서 읽는 일이 없다 (지금까지와 같음)
  - 예산을 넘으면 이전·현재·다음 곡만 RAM에 둔다. 곡을 넘기면 그다음 곡을 바로 디코딩하기 시작하므로, 한 곡을 연주하는 동안 다음 곡이 준비된다
  - 예산: 환경 변수 `B4ND_MEDIA_BUDGET_MB`, 없으면 PC RAM의 절반 (최대 12 GB)
  - 메모리 해제는 엔진이 이전 재생 계획을 돌려준 뒤 메시지 스레드에서만 한다 (오디오 스레드에서 큰 메모리를 풀지 않음)
- 공연 안전
  - 오디오가 아직 RAM에 없는 곡은 재생하지 않는다 ("PLAY refused ... still loading" 기록). MR이 빠진 채로 PA에 나가는 것보다 낫다
  - 공연 화면: NEXT 옆에 "LOADING 2/7" 또는 "AUDIO MISSING", 현재 곡이 준비 전이면 "LOADING SONG AUDIO"
  - 좌측 곡 목록에도 LOADING / NOT IN RAM / MISSING 표시
- 검증 (Linux 로컬, CI에 같은 검사)
  - 곡 4개 만들기, 순서 바꾸기, 이름 바꾸기 → 저장 → 다시 열기에서 순서·이름 유지
  - 예산 26 MB(곡 3개 분량)로 열기: WINDOWED, 멀리 있는 곡은 not in RAM, 4번 곡을 고르면 로딩되기 전 PLAY 거부, 로딩 후 재생
  - Windows CI: 같은 흐름을 로그로 확인
- 남은 검증 (🪟): 실제 공연 분량(20곡 이상, 스템 포함)의 RAM 사용량, 곡 전환 직후 다음 곡 디코딩이 재생에 영향이 없는지 (Phase 14 장시간 테스트와 함께)
- 아직 없는 것: 세트리스트 여러 개(공연별), 곡 사이 자동 진행·간격, 드래그로 순서 바꾸기
